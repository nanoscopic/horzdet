# Horizon: Technical Findings Memorandum on the Provenance of the Rust Source

**Subject:** Evidence that the Horizon project (`github.com/horizon-rust/horizon`) is a translation/derivative of decompiled *Minecraft: Java Edition 26.3* source, that it incorporates GPLv2 OpenJDK code under an MIT grant, and why its MIT license is unsafe to rely on.

**Prepared:** 2 November 2026
**Repository examined:** `horizon-rust/horizon`, default branch `main`, HEAD `68a348299e7e1f3f231397fa459936fc50084f26` (2026-11-02)
**Game artifacts examined:** official Mojang `26.3` client and server JARs, SHA-1 verified against the project's own `research-lock.json`
**Decompiler:** Vineflower 1.12.0 (the version the project itself pins)

> **Status of this document.** This is a technical findings memo, not legal advice, and not a legal opinion. It is written to be handed to counsel as a factual foundation. It separates what was *observed* from what counsel may *argue*. Nothing here has been tested in court. The author is not a lawyer.

> **Publication edition.** This version abridges long verbatim code excerpts to short quotations and line references, for commentary and analysis. The full working memo is retained privately. No third-party source files, jars, or decompiled trees are included. Quotations remain the property of their respective owners and are used for criticism and analysis.

## 1. Executive summary

Horizon is a ~1,026,000-line Rust reimplementation of Minecraft. Its public position is that it "contains no Minecraft code, assets or data" and is therefore MIT-licensed original work.

The repository's own tooling, documentation, commit history and source code contradict that position in a specific and cumulative way:

1. **The project's stated engineering method is translation, not clean-room reimplementation.** Its contributor guide tells authors to "Read the vanilla code before writing Horizon's." Its agent skill says: *"Translate the vanilla method, don't reinvent it: same order of operations, same constants, the same random draws in the same order."* Its own documentation describes "one-to-one" parity as the acceptance criterion.
2. **The repository pins the exact official game JARs and a decompiler, and ships the tooling to decompile them.** `research-lock.json` contains the SHA-1 of the official 26.3 client (`e877b6a0…`) and server (`33680f5f…`) and the SHA-256 of Vineflower 1.12.0 (`1dfcfe97…`). All three hashes were independently reproduced. `docs/decompilation-status.md` records a completed decompilation of 7,301 client and 5,037 server source files.
3. **The Rust source contains 6,490 inline citations of the form `` /// `Class.method` `` mapping Rust functions to specific Minecraft methods.** A 14,668-row `tools/port_map/*.tsv` ledger records, method by method, where each vanilla method is "ported", "inlined", "missing", or deliberately skipped. This is not a list of behaviors; it is a map of Minecraft's internal implementation.
4. **Large blocks of committed, MIT-licensed source are explicitly generated by copying vanilla source.** `crates/horizon-world/src/datafix/flat_tables.rs` begins: *"Lookup tables … copied from vanilla's sources by `tools/gen_flat_tables.py`. Do not edit."* `block_state_data.txt` (1,703 lines, 450 KB) is generated from `BlockStateData.java`.
5. **The build system compiles Java "exporters" against Minecraft and executes them to dump Minecraft's internal gameplay facts into Horizon's runtime data.** This is a data-extraction pipeline, not a clean-room specification.
6. **At least six independent subsystems reproduce idiosyncratic implementation choices that have no public specification and no reason to coincide in an independent implementation.** These are the "smoking guns" and are set out in §4. They include the `wrap` boundary and `1.0E-7F` fudge in Perlin noise, the `NormalNoise` statistical constants, a magic reciprocal-square-root constant, a 257-entry arctangent lookup table, and an A* heap whose tie-breaking determines which of several equal-cost paths is chosen. (The 16-entry Perlin gradient table is Perlin's published reference, not a Minecraft fingerprint; it is excluded.)
7. **The project applies the opposite rule to third-party code.** `CONTRIBUTING.md` says of other projects' source: "Don't read, copy, translate or paraphrase their source." `docs/modpacks.md` says a mod's code "is never decompiled, read, quoted or paraphrased, by people or agents." The project deleted ~19,190 lines of shader code in PR #1561 because it had been written from another project's source — the removal commit says the code "was written from Iris's source," and Iris is LGPL-3.0. It did not apply that rule to Minecraft.
8. **The result is that the MIT license is unauthorized as to the Minecraft-derived portions.** Downstream users, forks (724 at time of writing), distributors and the launcher's users receive no valid license to those portions from Horizon, and Horizon cannot grant one. That is the "radioactive" problem: the contamination propagates through the MIT grant.
9. **Separately, and more cleanly, the repository contains a port of GPLv2 OpenJDK/HotSpot code and distributes it under MIT.** `crates/horizon-core/src/jmath.rs` describes itself as "`java.lang.FdLibm` ports" and "HotSpot's tables, verbatim," and `crates/horizon-core/src/geometry/trig.rs` ports fdlibm's `asin`/`atan`/`atan2`. The OpenJDK files carry GPLv2 (the HotSpot trig file is GPLv2 *without* the Classpath Exception). GPLv2 §0 expressly defines a "work based on the Program" to include a work "translated into another language," and §2(b) requires the whole derivative to be distributed under the GPL. Horizon declares the workspace `license = "MIT"` and has no Oracle/OpenJDK/fdlibm notice. This claim does not depend on substantial similarity, abstraction-filtration, or fair use; it is a strict license-compatibility failure, admitted in the file headers.
10. **The removed shader crate is the single strongest finding, and it is still distributed.** In October 2026 Horizon shipped `crates/horizon-shaderpack` — 6,638 lines, 170 references to Iris, verbatim copies of Iris's `CommentDirectiveParser` test strings, and Iris's internal `iris_*` identifiers — under its MIT workspace. The removal commit (`4e7c25bb5`) admits: "A developer of Iris showed that Horizon's shader pack code was written from Iris's source." Iris is LGPL-3.0. The crate is gone from `HEAD` but remains reachable from `main` and 285 tags; a normal `git clone` still transfers it. The project did not rewrite history. See §4.8 and §3.10.

The cumulative case is strong for **derivative work by translation**. It is strongest where arbitrary constants, branch order, random-draw order and tie-breaking match; weakest where only generic algorithms or short strings match. §7 sets out the counterarguments candidly.

## 2. Method and reproducibility

### 2.1 What was done

1. Cloned the repository at HEAD (full history, 14,319 commits).
2. Downloaded the official 26.3 client and server JARs from Mojang's CDN.
3. Verified their SHA-1 against `research-lock.json` and against Mojang's version manifest.
4. Extracted the server's inner game JAR from the bundler.
5. Downloaded Vineflower 1.12.0 and verified its SHA-256 against `research-lock.json`.
6. Decompiled both JARs with the same flags the project uses (`--folder --skip-extra-files=1`).
7. Compared Rust functions against the decompiled Java **by reading both**, selecting methods where the Rust doc comment names a specific vanilla method.
8. Reconstructed the project's own decompilation counts as a control: 7,301 client source files and 5,037 server source files, exactly matching `docs/decompilation-status.md`.

## 3. Repository-level evidence

### 3.1 The stated method is translation

`CONTRIBUTING.md:35`:

> **Read the vanilla code before writing Horizon's.** `tools/rea_vanilla.py` queries the pinned game bytecode … Say in your pull request which vanilla classes and methods you followed.

`CONTRIBUTING.md:52`:

> Horizon is MIT. Its code is written from Minecraft 26.3 itself and from public documentation.

`.claude/skills/vanilla-parity/SKILL.md:44` (the instruction file loaded by AI agents working on the repo):

> **Translate the vanilla method, don't reinvent it:** same order of operations, same constants, the same random draws in the same order (`horizon_core::random`), Java `Math` through `horizon_core::jmath`.

`AGENTS.md:124`:

> Decompiled sources: `.local/minecraft/26.3/sources/{client,server}/` (`python3 tools/lab.py decompile`).

`docs/rust-parity.md:4`:

> One-to-one vanilla gameplay parity is the acceptance criterion.

These are not ambiguous. "Translate the vanilla method" and "same order of operations, same constants, the same random draws in the same order" describe the production of a derivative work in the copyright sense (17 U.S.C. § 101 defines a derivative work as one "based upon one or more preexisting works, such as a translation … or other form in which a work may be recast, transformed, or adapted").

### 3.2 The repository contains the decompilation pipeline

`docs/decompilation-status.md:3`:

> Verified on 2026-10-03 using the pinned official Java Edition 26.3 artifacts, Vineflower 1.12.0, and OpenJDK 25.

The same document records 11,383 client classes / 98,739 methods decompiled to 7,301 Java files, and 7,762 server classes / 72,269 methods to 5,037 files, with zero missing files and zero decompiler-error markers.

`research-lock.json` pins Vineflower and the exact JAR hashes. `tools/lab.py` contains the `decompile` command. `tools/rea_vanilla.py` drives a second decompiler (JADX via REA) over the bytecode.

### 3.3 The decompiled tree is deliberately kept out of Git

`AGENTS.md:9`:

> **Never commit Mojang's files**: game jars, assets, decompiled source, prepared resources (`.local/`).

`tools/check_public_tree.py` enforces this: it rejects `.java`, `.jar`, `.class` and the `.local`/`decompiled`/`minecraft` roots, with narrow allowlists for original Horizon Java tools.

This is consistent with two readings, and counsel should explore both:

- **Neutral reading:** the project knows it cannot redistribute Mojang's files and keeps them local.
- **Less neutral reading:** the project knows that the *derived* work (the Rust) is the valuable thing, and keeps the evidence of derivation out of the public tree while shipping the derivative.

Either way, the policy is an admission that the decompiled source exists and is used. The repository is not a clean-room: the decompiled source is a required input to the normal development workflow.

A scan of every blob in the full git history for the Vineflower `$VF:` error marker and for `net.minecraft.` in non-Java files found **no committed decompiled source**. The only `$VF:` string is a test fixture in `tests/test_lab.py` (`// $VF: Couldn't be decompiled`), and the `net.minecraft.` hits are the project's own Java oracles and documentation. The public tree is clean; the direct evidence of decompilation is in the gitignored `.local/` tree, on contributors' machines, and in the tools that generate and consume it (`tools/lab.py`, `tools/port_regen.py`, `tools/rea_vanilla.py`). That is where discovery should look.

### 3.4 The `port_map` is a method-level index of Minecraft's implementation

`docs/port-ledger.md` describes a tool that "pairs every vanilla method with the Rust fn that ports it". The TSV files contain 14,668 rows. A representative sample (`tools/port_map/game-001.tsv`):

```
ChunkGenerationTask.runUntilWait   inline  .../streaming.rs::Streaming::update   stages advance as worker results come back, not by waiting on futures
ChunkHolder.hasChangesToBroadcast  inline  .../lan/hub.rs::Hub::broadcast_block_changes   both broadcast fns return early when their log is empty
ChunkLevel.fullStatus              port    .../ticket_levels.rs::Levels::loaded_ticking   31 entity ticking, 32 block ticking, 33 full as predicates on Levels
```

These notes describe the vanilla implementation in enough detail to reconstruct it. The ledger's matching heuristics explicitly rely on copied rarities (`docs/port-ledger.md:62`):

> **Inferred:** nothing names it, but a function shares what is hard to share by chance: rare numbers (`0.458`, `72000`) and game ids …

A tool that matches Rust to Java by shared "rare numbers" is a tool built on the premise that the numbers were copied.

### 3.5 Committed source admits copying

`crates/horizon-world/src/datafix/flat_tables.rs:1`:

> Lookup tables of the DataFixers of 1.13 (DataVersion 1343 to 1631), **copied from vanilla's sources** by `tools/gen_flat_tables.py`. Do not edit.

`crates/horizon-world/src/datafix/block_state_data.rs:3`:

> The table itself is `block_state_data.txt`, **generated from vanilla's source** by `tools/gen_block_state_data.py`.

`tools/gen_flat_tables.py:2`:

> **Copy the lookup tables** of vanilla's flattening-era DataFixers (1.12.2 -> 1.13.2) into `crates/horizon-world/src/datafix/flat_tables.rs`, so that the Rust fixes use **exactly vanilla's data**.

These are committed, MIT-licensed files. The header alone defeats the README's "contains no Minecraft code, assets or data" claim as to at least these files. The tables are large: `flat_tables.rs` is 97 KB and 2,760 lines; `block_state_data.txt` is 450 KB and 1,703 lines.

### 3.6 The build executes Minecraft code to extract data

`crates/horizon-items/src/blocks.rs:1`:

> Per-state gameplay facts **exported from vanilla's own block-state accessors** (`gameplay-facts.json`), indexed by registry state ID.

The exporters are Java programs in `mods/horizon/src/test/java/dev/horizonlab/parity/` (e.g. `VanillaBlockBehaviourExporter.java`, `VanillaGameplayFactsExporter.java`). They are compiled against the Minecraft JAR and run by `horizon-prepare`. `crates/horizon-prepare/src/exporters.rs` bundles them and checks that only Horizon-authored classes are packaged, while the game JAR remains player-supplied.

This is a sophisticated laundering step: rather than committing a table of Minecraft's block properties, the project ships a program that asks Minecraft for the properties at install time. The output (`gameplay-facts.json`) is still Minecraft-derived data, and the exporters reach into non-public internals by reflection.

### 3.8 The double standard on third-party code

`CONTRIBUTING.md:50-66` sets out a detailed policy for other projects: only permissive licenses may be read; GPL, MPL, Polyform, all-rights-reserved and unlicensed code is "off limits, even to read"; "Don't read, copy, translate or paraphrase their source."

`docs/modpacks.md:147`:

> A mod's code is never decompiled, read, quoted or paraphrased, by people or agents.

`docs/modpacks.md:781`:

> Never its code: the agent doesn't decompile, read or quote it.

PR #1561 (`643f331f8`, 2026-10-24) removed ~19,190 lines of shader code because it "had been written from another project's source"; the shader packs were to return only as a "clean-room rewrite from a written description".

The project therefore understands the legal proposition perfectly: **reading and translating decompiled source contaminates the result**. It enforces that proposition against third parties. It exempts Minecraft, whose source has no license that permits any of this.

This is the single most useful fact for a willfulness argument. It is not a case of unsophisticated developers who did not know better. The knowledge is written into the contributor policy, applied once (shader packs), and deliberately not applied to Mojang.

### 3.9 The README's disclaimer

`README.md:29`:

> Horizon contains no Minecraft code, assets or data: you need your own copy of Java Edition 26.3.

For the reasons above, this statement is, at minimum, misleading as to the Rust source: the Rust source is a translation of Minecraft code, and at least two committed data files say so in their headers. Counsel should treat the disclaimer as a representation that can be tested against the repository's own admissions.

## 4. Algorithmic smoking guns

This section is the core of the memo. Each case compares a Rust function to the decompiled Java method it names in its own doc comment. The test applied is not "do they do the same thing" — behavior is generally not protectable — but:

> **Does the Rust reproduce an arbitrary, non-obvious implementation choice that an independent implementer had no reason to make, and that is only explicable by derivation?**

Generic algorithms (quicksort, A*, Perlin noise in the abstract) are expressly excluded. What follows is the opposite: choices that are idiosyncratic to Minecraft's codebase.

### 4.1 Perlin noise: the shuffle, the wrap boundary, and the statistical constants

**Files:**
- Java: `net/minecraft/world/level/levelgen/synth/GradientNoise.java`, `PerlinNoise.java`, `NormalNoise.java`, `SmearedPerlinNoise.java`
- Rust: `crates/horizon-core/src/noise/mod.rs`, `noise/perlin.rs`, `noise/normal.rs`

#### (a) The gradient table is not probative

Java (`GradientNoise.java`) declares sixteen 3-component vectors; the last four repeat entries 0, 9, 1 and 11. It is tempting to treat that as a Minecraft fingerprint, but it is not. Ken Perlin's published improved-noise reference uses a 16-slot table with four repeated directions, and GPU Gems chapter 5 explains why: the hash returns a 4-bit value, so 16 slots are defined and the extra four repeat `(1,1,0)`, `(-1,1,0)`, `(0,-1,1)` and `(0,-1,-1)`. Horizon's own comment says "Perlin's 16-direction table includes four repeated directions."

The only residual detail is the ordering: Minecraft's four repeats are 0, 9, 1, 11; GPU Gems lists 0, 1, 9, 11. That is a weak signal at best and should not be presented as a Minecraft-specific invention. The probative parts of this file are the constructor's draw order, the `wrap` boundary and the `NormalNoise` constants, below.

#### (b) The shuffle

Java (`GradientNoise`):

```java
this.offsetX = random.nextDouble() * noiseOffsetScale;
this.offsetY = random.nextDouble() * noiseOffsetScale;
this.offsetZ = random.nextDouble() * noiseOffsetScale;
for (int i = 0; i < 256; i++) this.perms[i] = (byte) i;
for (int i = 0; i < 256; i++) {
    int offset = random.nextInt(256 - i);
    byte tmp = this.perms[i];
    this.perms[i] = this.perms[offset + i];
    this.perms[offset + i] = tmp;
}
```

Rust (`noise/mod.rs:39-51`):

```rust
// Zero scale still consumes all three draws.
let offsets = std::array::from_fn(|_| random.next_double() * offset_scale);
let mut permutations = std::array::from_fn(|i| i as u8);
for i in 0..256 {
    let other = i + random.next_int_bound((256 - i) as i32).unwrap() as usize;
    permutations.swap(i, other);
}
```

The combination is what matters:

- Three `nextDouble` draws, in X/Y/Z order, *before* the shuffle. The Rust comment explicitly notes that a zero scale still consumes them — i.e. the author is tracking Java's draw count.
- A **forward** Fisher–Yates variant that draws `nextInt(256 - i)` and swaps `i` with `i + offset`. The textbook Fisher–Yates draws `nextInt(i + 1)` and iterates downward.
- The permutation array is initialized to `0..255` in order.

The forward variant is a known algorithm, not unique to Minecraft. What is probative is the exact draw order: the three offsets, in X/Y/Z order, before the shuffle, then `nextInt(256 - i)`, with the Rust comment tracking the zero-scale draw count. That combination matches `GradientNoise`'s constructor.

#### (c) `wrap`: a magic constant and a `nextDown` boundary

Java (`GradientNoise`):

```java
private static final int ROUND_OFF = 33554432;
private static final double HALF_ROUND_OFF = Math.nextDown(1.6777216E7);
return x >= -HALF_ROUND_OFF && x < HALF_ROUND_OFF
    ? x
    : x - Math.floor(x / 3.3554432E7 + 0.5) * 3.3554432E7;
```

Rust (`noise/mod.rs:112-119`):

```rust
pub fn wrap(value: f64) -> f64 {
    let half = f64::from_bits(16_777_216.0_f64.to_bits() - 1);
    if value >= -half && value < half {
        value
    } else {
        value - (value / 33_554_432.0 + 0.5).floor() * 33_554_432.0
    }
}
```

`3.3554432E7` is `2^25`. `1.6777216E7` is `2^24`. `Math.nextDown(2^24)` is reproduced bit-exactly as `from_bits(to_bits(2^24) - 1)`. The inclusive/exclusive comparison directions match. Again: arbitrary constants, arbitrary boundary semantics, exact reproduction.

#### (d) `computeFudgeY`: the float-to-double widening

Java (`SmearedPerlinNoise.java:43-52`):

```java
private double computeFudgeY(final double originalY, final double relativeY) {
   double fudgeLimit;
   if (originalY >= 0.0 && originalY < relativeY) fudgeLimit = originalY;
   else fudgeLimit = relativeY;
   return Mth.floor(fudgeLimit / this.fudgeYScale + 1.0E-7F) * this.fudgeYScale;
}
```

Rust (`noise/perlin.rs:331-338`):

```rust
fn compute_fudge_y(input_y: f64, relative_y: f64, scale: f64) -> f64 {
    let limited_y = if input_y >= 0.0 && input_y < relative_y {
        input_y
    } else {
        relative_y
    };
    f64::from(floor_i32(limited_y / scale + f64::from(1e-7_f32))) * scale

```

The decisive detail is `f64::from(1e-7_f32)`. Java writes `1.0E-7F`, a **float** literal, which is promoted to double for the addition. The promoted value is `9.99999993922529e-8`, not `1e-7`. The Rust author could have written `1e-7` (an f64) and been mathematically almost identical; instead they wrote an f32 literal and widened it, reproducing Java's exact rounding. That is a translation artifact, not an independent design choice.

The same file also reproduces the unusual split between the unfudged `alphaY` and the fudged corner offset (Java passes `fudgedRelativeY` for the corners but `(float) relativeY` for the smoothstep; Rust stores `fade: smoothstep(dy)` and `offset: fudged` separately).

Why this is probative:

- A 257-entry `asin` lookup table plus a bit-hack reciprocal square root plus a cubic correction is an unusual way to implement `atan2`. It is a specific performance trick from Minecraft's codebase, not a standard library algorithm.

- The correction polynomial coefficient `0.16666666666666666` (not `1.0/6.0`) and the `(6.0 + sd*sd) * sd` grouping match exactly.
- The branch order (`negY`, `negX`, `steep`, then the three corrections) matches exactly.

An independent implementation of `atan2` would call `f64::atan2` or use a polynomial approximation. It would not reproduce this table and this bit hack.

### 4.6 A* pathfinding: the 1.5 "fudging" factor and heap tie-breaking

**Files:**
- Java: `net/minecraft/world/level/pathfinder/PathFinder.java`, `BinaryHeap.java`, `Node.java`, `Target.java`
- Rust: `crates/horizon-client/src/mobs/path.rs:1172-1379`

This is the best example of a non-obvious algorithmic match because A* has many valid implementations, and the chosen path among equal-cost alternatives depends on arbitrary tie-breaking.

#### (a) The heuristic is multiplied by 1.5

Java:

```java
private static final float FUDGING = 1.5F;
...
neighbor.h = this.getBestH(neighbor, targets) * 1.5F;
```

Rust:

```rust
let h = self.best_h(neighbor, &mut targets) * 1.5;
```

A* normally uses an admissible heuristic with weight 1.0. Minecraft deliberately inflates it by 1.5 ("fudging") to trade optimality for speed. The constant is not in any algorithm textbook; it is a Minecraft tuning choice. Reproducing it is probative.

#### (b) The search loop order and side effects

Java:

```java
while (!openSet.isEmpty()) {
   if (++count >= maxVisitedNodesAdjusted) break;
   Node current = openSet.pop();
   if (!reached.isEmpty()) break;
   neighbor.walkedDistance = current.walkedDistance + distance;
   neighbor.h = getBestH(neighbor, targets) * 1.5F;
}
```

*(Abridged; the full loop is in `PathFinder.java`. The point is the order of the lines, not the omitted bodies.)*

Rust:

```rust
while !self.heap.is_empty() {
    count += 1;
    if count >= max_visited { break; }
    let current = self.heap_pop();
    self.nodes[neighbor].walked = walked;
    let h = self.best_h(neighbor, &mut targets) * 1.5;
}
```

*(Abridged; the full loop is in `mobs/path.rs`.)*

Every detail matches:

- `walkedDistance` is assigned unconditionally **before** the open-set/improvement test, so it mutates even for rejected neighbors.
- The target-reached check is inside the main loop, before the distance check, and breaks out of the whole search.
- `count` is incremented and compared with `>=`, matching Java's `++count >= ...` off-by-one.
- The heuristic update happens **before** the open/set branch, and `changeCost` receives `g + h`.

None of this is required by "find a path". It is required by "find *the same* path as vanilla for the same world and seed".

#### (c) The binary heap

Java `BinaryHeap` and Rust `heap_insert`/`heap_pop`/`change_cost`/`up_heap`/`down_heap` are structural mirrors:

- Nodes carry a `heapIdx`/`heap` back-pointer, updated on every move.
- `upHeap` breaks when `!(cost < parent.f)` — i.e. equal costs do **not** swap.
- `downHeap` treats a missing right child as `+Infinity`, and on `leftCost < rightCost` prefers the left child; equal children prefer the right. This exact tie rule changes pop order.
- `pop` moves the last element to the root, then sifts down.
- `changeCost` compares the new cost to the old and sifts up or down.

A Rust implementation using `std::collections::BinaryHeap` (a max-heap) with an `Ord` wrapper would produce a different tie order, and therefore different paths. Horizon did not do that; it reimplemented Minecraft's heap, including the back-pointers and the exact comparison directions.

The Java `BinaryHeap.insert` even throws `IllegalStateException("OW KNOWS!")` on a double insert — a joke string. The Rust does not carry the string, but it does carry the `heapIdx >= 0` invariant that the string guards.

Git history states the provenance:

- `558d140fc` (2026-10-13): *"Compute Math.sin/cos/pow/log10 as HotSpot does on the host architecture"*
- `7826a221c` (2026-10-13): *"jmath: satisfy clippy (fdlibm's constants and NaN idiom, verbatim)"*
- `d385d188f` (2026-10-29): *"fix(core): atan2 matches StrictMath"*
- `5815bf4f1` (2026-10-29): *"jmath::atan2: use the fdlibm port geometry::trig already has"*

#### (d) The license failure

GPLv2 §0 defines the scope expressly:

> The "Program", below, refers to any such program or work, and a "work based on the Program" means either the Program or any derivative work under copyright law: that is to say, a work containing the Program or a portion of it, either verbatim or with modifications and/or **translated into another language**.

A Java-to-Rust port is therefore a "work based on the Program" by the license's own definition. GPLv2 §2(b) then requires:

> You must cause any work that you distribute or publish, that in whole or in part contains or is derived from the Program or any part thereof, to be licensed as a whole at no charge to all third parties under the terms of this License.

Horizon instead declares the whole workspace MIT (`Cargo.toml:43`, `license = "MIT"`; `crates/horizon-core/Cargo.toml` inherits it), and `THIRD_PARTY_NOTICES.md` contains no mention of Oracle, OpenJDK, Sun, fdlibm, GPL, or the Classpath Exception. The result is a distribution of a GPL-derived work under a non-GPL license, without the GPL text, source-offer, or notices.

The Classpath Exception does not cure this:

- It is an exception for **linking** GPL library code with independent modules, not for copying or translating the GPL source into the module.
- The HotSpot `macroAssembler_aarch64_trig.cpp` file carries **GPLv2 only**; its header does not include the Classpath Exception.
- Even on the most charitable reading — that the Rust is a port of the original C fdlibm rather than of OpenJDK's Java port — the original fdlibm license requires the Sun copyright notice to be preserved ("provided that this notice is preserved"), and no such notice appears. The file comments say "fdlibm's constants and NaN, verbatim" while omitting the notice.

#### (e) Why this matters more than the Minecraft claim

- **No substantial-similarity fight.** The defendant's own comments identify the source and say "verbatim."
- **No fair-use escape of the same kind.** Fair use is a defense to copyright infringement; it does not rewrite the GPL's distribution conditions. A GPL violator cannot cure the violation by arguing the copying was fair use.
- **Strict liability.** Distributing the code under MIT is the violation; intent is irrelevant to liability (though relevant to damages).
- **An independent claimant.** Oracle owns the OpenJDK copyrights. Microsoft's claim is about Minecraft; Oracle's is about the JDK. The two claims reinforce each other and make the "radioactive" problem worse for downstream users.
- **It taints the whole binary.** `horizon-core` is a dependency of the client, the server and the launcher's preparer. The GPL-derived code is not isolated in a test utility.

A defendant may argue that the Rust is an independent reimplementation of fdlibm's published algorithms and that the OpenJDK similarity is structural coincidence. That argument is weakest for the AArch64 `kernel_cos` register-reuse quirk and the `FdLibm` class/method naming, and it does not answer the missing fdlibm notice.

### 4.8 Shader packs: the removed crate is an admitted port of Iris (LGPL-3.0)

This is the strongest copying evidence in the repository, because it does not rest on inference: the project's own removal commit says the code "was written from Iris's source."

#### (a) The admission

On 2026-10-24, commit `4e7c25bb5` ("Remove shader packs", merged as PR #1561 / `643f331f8`) deleted `crates/horizon-shaderpack` and the Java-pack loading, render stages, Shader Packs screen, launcher browsing/installing, docs and examples. The commit message:

> A developer of Iris showed that Horizon's shader pack code was written from Iris's source. This removes it: the horizon-shaderpack crate, Java pack loading and its render stages, Horizon's own WGSL packs and the example packs, the Shader Packs screen and its option, the launcher's shader pack browsing and installing, and the docs about them. Shader packs may come back later as a clean-room rewrite.

That is a party admission, in the repository, by the maintainer, that the code was copied from Iris. The same admission is on the project's public documentation page, `docs/how-horizon-is-built.md`:

> On 24 October shader packs were removed ([#1561](https://github.com/horizon-rust/horizon/pull/1561)), after a developer of Iris showed that our shader pack code had been written from Iris's source. They are being written again from a description of the pack format only.

That is not a buried commit message; it is the page the project points users to for "how it's built" and "why it's safe to run."

#### (b) What was deleted

The deleted crate was not a small experiment:

- `crates/horizon-shaderpack/Cargo.toml` describes it as: *"Java (OptiFine/Iris) shader packs for Horizon: **Iris's preprocessor** and the GLSL to WGSL translation."*
- Nine source files, **6,638 lines**: `include.rs` 187, `lib.rs` 191, `options.rs` 639, `pipeline.rs` 1,025, `preprocess.rs` 571, `properties.rs` 1,009, `source.rs` 146, `translate.rs` 2,073, `uniforms.rs` 797. Two test files add 1,165 lines.
- **170 occurrences of "Iris"** in the source.
- Iris class names throughout: `IncludeGraph`, `IncludeProcessor`, `AbsolutePackPath`, `FileNode`, `ShaderProperties`, `PropertiesPreprocessor`, `OrderBackedProperties`, `OptionAnnotatedSource`, `ParsedString`, `OptionSet`, `ProgramDirectives`, `PackRenderTargetDirectives`, `CompositeRenderer`, `CustomUniforms`, `IrisFunctions`, `SmoothFloat`, `IrisLimits.MAX_COLOR_BUFFERS`, `InternalTextureFormat`, `BufferFlipper`, `StandardMacros`, `IrisDefines`, `Iris.loadExternalZipShaderpack`.
- Iris's internal identifiers: `iris_ModelViewMatrix`, `iris_ProjectionMatrix`, `iris_NormalMatrix`, `iris_TextureMatrix`, `iris_FogFragCoord`, `iris_FrontColor`, `iris_TexCoord`, `iris_FragData`, `iris_mod`, `iris_modf`, `iris_isnan`, `iris_isinf`, `iris_mat2`, `IRIS_HAS_TRANSLUCENCY_SORTING`, `IRIS_REQUIRES_SEPARATE_ENTITY_DRAWS`, `IS_IRIS`.
- Commit titles in the series: `b22583d05` "open Java shader packs and preprocess them **like Iris**", `38a9f6543` "read shaders.properties **like Iris**", `e1d9ae1dd` "plan a Java pack's full-screen passes **like Iris**", `98ebdcad7` "translate Java shader pack programs to WGSL", `2862f17e8` "run a Java pack's full-screen passes over the world", plus `0431f12a6` "Give Java packs' full-screen passes **Iris's** sky, eye light and custom uniforms".

#### (c) Verbatim test cases

The most vivid evidence is that the Rust copied Iris's **unit-test inputs**. `pipeline.rs:954` says:

```rust
// Iris's own cases (`CommentDirectiveParser.Tests`).
```

and then uses the strings from Iris's `CommentDirectiveParser.java` `Tests.main`:

| Horizon `pipeline.rs` | Iris `CommentDirectiveParser.java` |
|---|---|
| `"Some normal text that doesn't contain a DRAWBUFFERS directive"` | `"Some normal text that doesn't contain a DRAWBUFFERS directive of any sort"` |
| `"doesn't contain a /* DRAWBUFFERS: directive of any sort"` | `"Some normal text that doesn't contain a /* DRAWBUFFERS: directive of any sort"` |
| `"/*DRAWBUFFERS:321*/ OptiFine will detect this"` | `"/*DRAWBUFFERS:321*/ OptiFine will detect this directive, but ShadersMod will not..."` |
| `"This is a line /* DRAWBUFFERS:31 */ containing"` | `"This is a line /* DRAWBUFFERS:31 */ containing a drawbuffers directive"` |
| `"    /*DRAWBUFFERS:12*/"` | (Iris's spacing case) |

The Horizon strings are Iris's test sentences with the tail cut off. Copying another project's test data is difficult to explain as independent implementation, because the strings are arbitrary and serve no compatibility purpose.

The function itself is the same algorithm, step for step. Horizon's `comment_directive` (`pipeline.rs:86`) and Iris's `CommentDirectiveParser.findDirective`:

| Step | Iris | Horizon |
|---|---|---|
| Find the last directive | `haystack.lastIndexOf(prefix)` | `text.rfind(&prefix)` |
| It must start a comment | `haystack.substring(0, indexOfPrefix).trim().endsWith("/*")` | `text[..at].trim_end().ends_with("/*")` |
| Find the end | `haystack.indexOf("*/")` | `rest.find("*/")` |
| Take and trim the value | `substring(0, indexOfSuffix).trim()` | `rest[..end].trim()` |

That is what a Java-to-Rust translation looks like: the same branches, the same string operations, the same order, with Rust idioms substituted for Java ones. The test strings are the inputs it was tested against.

The include-path resolver is the same story. Both split on `/`, skip empty and `.` segments, pop on `..`, and join the rest (`include.rs::resolve` vs `AbsolutePackPath.normalizeAbsolutePath`). The Rust `parts.pop()` is a no-op on an empty vector, so it matches Java's `if (!parsedSegments.isEmpty()) removeLast()`. Again: the same algorithm with different syntax.

The same pattern appears in:

- **`preprocess.rs`** — copies `StandardMacros` names (`IRIS_REQUIRES_SEPARATE_ENTITY_DRAWS`, `IRIS_HAS_TRANSLUCENCY_SORTING`, `MC_GL_RENDERER_GEFORCE`, `MC_GL_RENDERER_RADEON`, etc.).
- **`options.rs`** — copies `OptionAnnotatedSource`'s `VALID_CONST_OPTION_NAMES` list (`shadowMapResolution`, `generateShadowMipmap`, `shadowHardwareFiltering`, `entityShadowDistanceMul`, ...).
- **`translate.rs`** — copies transform strings from `DHGenericTransformer` / `CompositeTransformer` / `CompositeCoreTransformer` (`mat4 iris_ProjectionMatrixInverse`, `mat4 iris_ModelViewMatrixInverse`, `mat3 iris_NormalMatrix`, ...).

#### (d) The licence chain

- **Iris is LGPL-3.0** (`iris-repo/LICENSE`, verified).
- Horizon's workspace declares `license = "MIT"` (`Cargo.toml`), and the crate inherits `license.workspace = true`. The pre-removal tree thus distributed an Iris-derived crate under MIT.
- `THIRD_PARTY_NOTICES.md` contains no Iris, LGPL or AGPL entry.
- Horizon's own `CONTRIBUTING.md:53-60` lists **"LGPL (Iris)"** and **"AGPL"** among the licences that are "off limits, even to read."
- Iris's `LICENSE-DEPENDENCIES` warns that `glsl-transformer` is **AGPL-3.0**. Horizon's `translate.rs` says it rewrites "the way Iris's glsl-transformer patches do." If any of that code is ported, AGPL applies on top of LGPL.

#### (e) Removal does not cure the distribution

The code is gone from `HEAD` but not from the repository:

- `b22583d05` (the introducing commit) is an **ancestor of `HEAD`** (`git merge-base --is-ancestor` returns 0).
- `git cat-file -e HEAD:crates/horizon-shaderpack/src/lib.rs` fails, but `git show b22583d05:crates/horizon-shaderpack/src/lib.rs` succeeds.
- The blob appears in `git rev-list main --objects`.
- **285 tags** contain `b22583d05`; `refs/heads/main`, `origin/main` and `origin/HEAD` all contain it. There is no shallow file or replace ref, so the current refs show no purge: any history rewrite the project may have done did not remove the code from the published refs, and it has not asked GitHub to purge cached objects or forks.
- **166 of those tags** point to commits that contain the crate and predate the removal, from `v2026.10.16.02` through `v0.2.46` (verified: `git cat-file -e v0.2.46:crates/horizon-shaderpack/src/lib.rs` succeeds). The crate therefore shipped in tagged builds, not just in the history.

A normal `git clone` transfers the whole reachable object graph, so **every clone of `main` still receives the Iris-derived code**, even though the working tree at `HEAD` does not show it. The same is true of the 285 tags and of existing forks (724 at time of writing). Removing a file in a later commit is not a distribution cure; it is a change to the tip.

#### (f) Why this is the strongest claim

- It is **admitted**: the maintainer says the code "was written from Iris's source."
- It is **concrete**: verbatim test strings, macro names, option names and Iris identifiers.
- It is **a licence violation on its face**: LGPL-3.0 code distributed under MIT, with no notice.
- It is **willful**: the removal happened only after an Iris developer showed them, and the commit documents that knowledge.
- It is **continuing**: the history is still served to every clone.

The "clean-room rewrite" that followed is not a cure for the old code. It also still carries Iris references (`shader_packs.rs:245` "Iris shades no faces by default", `macros.rs`, `preprocess.rs`), so its independence should be tested, not assumed.

### 4.9 The "clean-room" rewrite and its missing specification

After removing the crate, the project began a second shader implementation, `crates/horizon-shaders`, in a series of commits labelled "clean room 1" through "clean room 42" (and later merges) between 24 and 26 October 2026. The new crate's header says:

> Shader packs: the `shaderpacks/*.zip` format, written from Horizon's clean-room specification (`shader-packs-spec.md`, revision 1).

The commits are more specific. `ac47b988c` says:

> Clean-room: implemented from cleanroom/shader-packs-spec.md revision 1, §2.4, §3.2; no other loader's code read.

But the specification is **not in the repository, and never was**. A search of every commit for `shader-packs-spec` and `cleanroom/` finds only the references in `lib.rs`, `AGENTS.md` and commit messages; no file named `shader-packs-spec.md` (or a `cleanroom/` directory) is added in any commit. `.gitignore` ignores only `/.local/`.

Why this matters:

- A clean-room defense depends on the spec being independent of the original. If the spec was written by the same person or agent from Iris's code (or from the removed crate), the implementation is still derivative — the "tainted spec" problem. The public tree gives no way to tell.
- **69 commits in three days** (10 on 24 October, 42 on 25 October, 17 on 26 October) is a very fast implementation, consistent with AI agents. The spec may have been generated by an AI that had Iris or the old crate in context; the agent transcripts would show.
- The new crate still contains "Iris" references (`macros.rs`, `preprocess.rs`, `config.rs`, `shader_packs.rs`) and implements `IS_IRIS` / `IRIS_FEATURE_*`. Some are required for compatibility; they are not proof of copying, but they show the rewrite is not independent of Iris's interface.
- The old crate is still in history, so a "clean-room" author could have consulted it. The spec is the only evidence that they did not.

What to ask for in discovery:

1. `shader-packs-spec.md` at revision 1, and every draft/revision.
2. The `cleanroom/` directory, or wherever the spec lives.
3. The AI agent transcripts for the 69 clean-room commits.
4. The commit authors' attestations of what they read.
5. A module-by-module comparison of the new crate against the old crate and Iris.

Until the spec is produced, the clean-room claim is **unverified**. That does not make the new code infringing; it means the project has not met the evidentiary burden its own defense requires. The old code's admission remains the primary finding.

A structural comparison of the new crate against the deleted one is, for what it is worth, consistent with a genuine rewrite: 40 function names in common out of 204 old and 346 new, only 20 of them non-generic (`preprocess`, `draw_buffers`, `locate`, `options`, `source`), and **no shared comment lines**. The 80 shared string literals are overwhelmingly shader-format identifiers (`gbuffers_*`, `shadowMapResolution`, `iris.features.*`, GLSL built-ins) that any compatible implementation must use. That weakens the theory that the new code is a straight re-skin of the old crate. It does not establish independence, because the spec that would prove it is missing.

`block_state_data.txt` (450 KB) maps every 1.12 `blockId << 4 | data` to its 1.13 block state, generated from `BlockStateData.java`. The header says so. The file is committed.

### 5.3 Port ledger

`tools/port_map/*.tsv` (90 files, 14,668 rows) is a database of Minecraft's method-level API and behavior. It is a compilation of Minecraft implementation facts. Even if individual method names are not protectable, the selection and arrangement — every method of every class, with a verdict and a note — is a candidate for compilation protection.

### 5.4 Language strings

The Rust source embeds Minecraft translation keys and their English values as fallbacks, e.g. `lang::get_or("selectWorld.backupWarning.downgrade", "This world was last played in version %s; you are on version %s. …")`.

A rough scan found **1,044** English values of length ≥ 6 from the official `en_us.json` appearing verbatim in the committed Rust, and **137** exact key+value pairs in `get_or(...)` calls. This is weaker evidence than the algorithmic matches (short strings and functional labels may not be protectable, and many are necessarily identical for compatibility), but the long warning paragraphs in `title.rs` are creative expression, not functional labels. Counsel should treat them as a secondary line, not the main case.

### 5.5 OptiFine: decompiled and compared; the claim is not supported in the sampled modules

**Status: checked, no copying found in the modules sampled; the Iris developer's specific claim remains unverified.**

A developer associated with Iris is reported to have said, in the project's Discord, that Horizon lifted methods from OptiFine for graphics efficiency. The claim could not be retrieved (it is in Discord, not a public issue or commit), and the official `sp614x/optifine` repository contains only documentation and workflow files, not source.

To test it, I downloaded the latest OptiFine build that targets a version near Horizon's (`preview_OptiFine_26.2_HD_U_K2_pre5.jar`, 7.8 MB), extracted its 762 compiled `srg/net/optifine/**` classes, and decompiled them with Vineflower 1.12.0 using the same flags used for Minecraft. I then compared the modules Horizon implements.

| Area | OptiFine (decompiled) | Horizon (Rust) | Result |
|---|---|---|---|

| Random variant pick | `rand = Config.getRandom(pos, face) & 0x7fffffff`, then `randomLoops` iterations of `Config.intHash` (a specific five-step hash), then `rand % total`. | `lowbias32` `mix()` with a golden-ratio step, different loop, then `% total`. | **Different hash and structure.** |

In the sampled areas, the code is independently implemented. Several of the differences are the kind that would not survive a copy: Horizon uses a different hash (`lowbias32` vs OptiFine's `intHash`), a different entity seed (UUID hash vs the low 31 bits of the UUID), and a completely different culling architecture. This **argues against** a wholesale OptiFine copy in these modules.

That does not disprove the Iris developer's claim. The claim may concern:

- modules I did not sample (the CEM model parser `cem/model.rs`, emissive textures, CIT, block culling);
- a specific OptiFine version or a specific method the claimant named;
- behavior (the tile tables, the option defaults) rather than code.

**What to do with the lead:** obtain the Discord message and the specific version/method it names; decompile that version; compare that method. Until then, the OptiFine allegation should sit in the "lead" column. It should not be presented to counsel as established, and the negative results above should be disclosed alongside it.

## 6. Legal analysis

> The following is a framework for counsel, not a legal opinion. It sketches theories and the facts that support or undermine them.

### 6.0 GPLv2: the license-compatibility claim (the strongest one)

Before the Minecraft copyright analysis, consider the simpler claim. It does not require proving that Rust is substantially similar to Java in the sense of *Altai*; it only requires showing that the Rust is a translation of GPL code and is distributed under MIT.

**The rule.** GPLv2 §0 defines a "work based on the Program" to include a work "translated into another language." GPLv2 §2(b) requires any distributed work "that in whole or in part contains or is derived from the Program or any part thereof" to be "licensed as a whole at no charge to all third parties under the terms of this License." §4 provides that any violation terminates the license.

**The facts.** `jmath.rs` and `trig.rs` are translations of OpenJDK's `java.lang.FdLibm` and HotSpot's AArch64 trig stubs. The file comments say "verbatim" and name the OpenJDK class/method and the HotSpot generator. The repository distributes the workspace under MIT, with no GPL text, no Oracle/OpenJDK notice, and no source offer for the GPL portions.

**The conclusion.** The MIT grant is ineffective as to the GPL-derived code. Horizon had no right to license that code under MIT, and it did not comply with GPLv2's conditions for distributing it. Oracle (and the OpenJDK contributors) have a copyright claim independent of Microsoft's Minecraft claim.

**The Classpath Exception does not save it.** The Classpath Exception is a linking exception: it lets independent modules link with the GPL library and be distributed under other terms, provided the library itself remains under the GPL and is not modified. It does not permit copying or translating the GPL source into the independent module. In any event, the HotSpot `macroAssembler_aarch64_trig.cpp` file is GPLv2 **without** the Classpath Exception, so the `aarch64` module has no exception to rely on at all.

**The fdlibm counter.** A defendant may argue that the Rust is a port of the original C fdlibm, not of OpenJDK's Java port, and that fdlibm's original license is permissive. Two problems:

1. The comments name `java.lang.FdLibm` and `MacroAssembler::generate_dsin_dcos`, not the C files.
2. Even the original fdlibm license requires the Sun notice to be preserved; no such notice appears in `jmath.rs`, `trig.rs` or `THIRD_PARTY_NOTICES.md`.

**The de minimis counter.** GPL has no de minimis exception. A single copied function is enough to make the distribution non-compliant. Here the copied code is in `horizon-core`, a dependency of the client, server and preparer — not an isolated test helper.

**Why it matters for the "radioactive" thesis.** A downstream user who receives Horizon under MIT does not receive a GPL license either, because Horizon never included the GPL terms. So the downstream user is also distributing GPL-derived code without a license. The contamination propagates through the MIT grant exactly as with the Minecraft code, but the GPL claim is easier to prove because the source is public and the comments admit the provenance.

**A compliance path (for completeness).** The project could relicense `horizon-core`'s GPL-derived modules under GPLv2, keep the rest under MIT, include the GPL text and notices, and provide the corresponding source. It has not done so. The point for counsel is not that compliance is impossible; it is that the current distribution is non-compliant, and the public MIT badge misrepresents the license status of the whole.

### 6.1 Copyright: translation is a derivative work

The strongest theory is **derivative work**. 17 U.S.C. § 101 defines a derivative work as one "based upon one or more preexisting works, such as a translation, musical arrangement, dramatization, fictionalization, motion picture version, sound recording, art reproduction, abridgment, condensation, or any other form in which a work may be recast, transformed, or adapted."

A Java-to-Rust translation of the same method, preserving operation order, constants, random-draw order and control flow, is a translation. The fact that the target language is different and the code is idiomatic Rust does not avoid derivation; it is precisely what a translation is. The repository's own instruction — "Translate the vanilla method, don't reinvent it" — is an admission of the required intent.

The Minecraft JAR is a copyrighted computer program. Mojang owns the copyright. Horizon's authors had access (they decompiled it). The Rust code is substantially similar at the level of protected expression: sequence, structure, organization, arbitrary constants, error behavior and internal data flow. The `port_map` is a roadmap of that similarity.

### 6.2 Non-literal similarity: abstraction-filtration-comparison

Courts in the Second Circuit use the abstraction-filtration-comparison test (*Computer Associates v. Altai*, 982 F.2d 693 (2d Cir. 1992)). The question is whether, after filtering out unprotectable elements (ideas, functional requirements, standard techniques, public-domain components), a substantial portion of protected expression remains.

Horizon's best defense is that its code is filtered: Rust idioms, different data structures, different naming, no literal Java. But the six case studies in §4 survive filtration because they are **not** standard techniques:

- A 16-entry gradient table with Minecraft's exact duplicates is not required by the Perlin algorithm.
- A forward Fisher–Yates shuffle with `nextInt(256-i)` is not standard.
- `3.3554432E7`, `0.101`, `-7.0E-4`, `1.5` fudging, and `0.2702247831245211` are arbitrary.
- The `TrapDoorBlock` redstone special case is a game rule, not a physics necessity.
- The A* heap tie-breaking is an implementation choice, not an algorithmic requirement.

Those are the "protected expression" residues. The cumulative pattern across 6,490 cited methods makes the qualitative case; the constants make it concrete.

### 6.3 Fair use

Horizon will likely argue fair use (17 U.S.C. § 107), relying on the intermediate-copying cases: *Sega v. Accolade*, 977 F.2d 1510 (9th Cir. 1992), and *Sony v. Connectix*, 203 F.3d 596 (9th Cir. 2000), which held that disassembly for interoperability can be fair use; and *Google v. Oracle*, 593 U.S. 1 (2021), which held Google's copying of Java API declarations into Android was fair use.

The counterarguments are strong:

- **Purpose and character.** Horizon is not an interoperability layer; it is a replacement game, distributed commercially/at scale (launcher, website, 5.7k stars, 724 forks). It is not "transformative" in the *Google* sense; it substitutes for the original.
- **Amount.** This is not 11,500 lines of API declarations. It is over a million lines of implementation, including data tables and internal algorithms. The copying is wholesale.
- **Market effect.** It competes with Minecraft and may cannibalize sales; it also creates a derivative product that Mojang does not control.
- **Nature of the work.** Minecraft is a creative computer program, not a functional API.
- **Bad faith.** The project's own double standard for third-party code, and its deliberate exclusion of `.java` from Git, cut against good faith. **This is the most damaging fact for fair use.** A project that says "don't translate other people's code" while translating Mojang's cannot easily claim it thought translation was fair.

*Google v. Oracle* is distinguishable: the copied declarations were necessary to use the Java language and were a fraction of the work; here the copied material is the game's implementation, and Horizon does not need it to interoperate.

### 6.4 Contract: EULA and Terms of Use

The Minecraft EULA and Microsoft account terms restrict reverse engineering and commercial exploitation. Decompiling the JAR and translating it likely breaches those terms. Whether Mojang can enforce them against a non-user (Horizon requires users to own Minecraft, so the developers are likely licensees) is a contract question; the EULA is a license, and exceeding its scope is copyright infringement, not merely breach (*Sun Microsystems v. Microsoft*, 188 F.3d 1115 (9th Cir. 1999)).

The README itself acknowledges the EULA and Mojang's ownership, which undercuts any argument that the authors were unaware of the license.

### 6.5 DMCA § 1201

If the JAR is protected by a technological measure (it is not strongly encrypted, but the EULA and the launcher's integrity checks may qualify), circumvention could be a separate claim. This is weaker than the copyright claim and should be pleaded cautiously. The more relevant DMCA provision is **§ 512** for takedowns of the GitHub repository and forks.

### 6.6 Trademark

The project uses "Minecraft" in its README badge, describes itself as "Minecraft: Java Edition 26.3 rewritten in Rust", and uses the name in the launcher and website. Nominative fair use may cover accurate references, but the overall presentation ("the game you know, rebuilt in Rust", the Minecraft badge) risks confusion about affiliation. The README's disclaimer helps, but it is not dispositive. This is a secondary claim.

### 6.7 Why the MIT license is invalid as to the derivative portions

Horizon's `LICENSE` grants MIT rights to "the Software" with copyright to "Ludovic Marie and the Horizon contributors". Horizon cannot grant rights it does not have. To the extent the Rust is a derivative of Minecraft:

- The MIT grant is **unauthorized** as to the Minecraft-derived elements.
- Downstream recipients (forks, distros, mod authors, launcher users) receive no valid license from Horizon for those elements.
- Horizon's own contributors may face claims; the project's warranty/indemnity is nonexistent.
- The contamination is not curable by adding a notice after the fact; the code remains derivative.

This is the "radioactive" point: the MIT badge is not a clean title. Anyone building on Horizon inherits the risk.

### 6.8 The "clean room" pattern: an AI rewrite does not launder copied code

The repository shows a repeating sequence:

1. Code is taken from a project whose license does not permit it (Iris, LGPL-3.0; OpenJDK, GPLv2; Minecraft, proprietary).
2. When the taking becomes visible, the code is quarantined, deleted, or removed from `HEAD`.
3. A "clean-room rewrite" is commissioned, often from an AI agent, and the project announces that the new code was written "from a specification."
4. The specification is not published; the old code remains in git history; the new code is declared MIT.

The examples are documented above:

- **Iris.** `4e7c25bb5` admits the shader code "was written from Iris's source." Then 69 commits labelled "clean room 1" through "clean room 42" land in three days (10 on 24 October, 42 on 25 October, 17 on 26 October), citing `cleanroom/shader-packs-spec.md` revision 1 — a file that is not in the repository or its history. The new crate is `crates/horizon-shaders`.
- **YUNG / Lithostitched / CTOV.** `486df91b2` quarantines the conversion code in `legacy_structure_mods/` "so a clean-room rewrite can replace the module"; `379692f35` and `c43f4bdb2` delete the legacy modules and add "clean-room" replacements, with commit messages stressing "no mod source read" and "the legacy files were deleted unread." The specs they cite are not in the repository.
- **Cull Leaves.** `717acb07a` removes code "adapted from the CullLeaves mod" (MIT, credited). That one was licensed, so it was compliant; it is part of the same sweep.
- **Minecraft.** The whole project is a translation, by the project's own description; the "clean room" here is the parity harness, not an independent implementation.
- **OpenJDK.** `jmath.rs` and `trig.rs` are "verbatim" ports, by their own comments.

#### (a) What a clean room actually requires

A clean-room (Chinese-wall) development has two separated teams:

1. **Specification team.** Reads the original and writes a description of its *behavior* — inputs, outputs, edge cases, protocol — at a level of abstraction that does not capture protected expression.
2. **Implementation team.** Has never seen the original, and implements from the specification alone.

The specification must be preserved, and the separation must be documented. If the same person or agent reads the original and writes the implementation, there is no clean room. If the specification is a line-by-line description of the original's structure, constants, branch order or internal names, the implementation is still derivative. This is the **tainted-spec** problem: a spec derived from protected expression transmits the derivation.

#### (b) The context problem: the original code was allowed into the session

The decisive question is not whether the new code differs in places; it is **what the implementing agent could see**. A clean room is defined by information isolation, not by the output's novelty.

Horizon's agents are not isolated:

- **The old code is in the same repository.** The removed crate is in `.git`; `git show b22583d05:crates/horizon-shaderpack/src/pipeline.rs` returns it. Any agent working in the checkout can read it, and the project's history is part of the context.
- **The decompiled sources are a documented input.** `AGENTS.md` points agents at `.local/minecraft/26.3/sources/{client,server}` and `tools/rea_vanilla.py`; the same pattern applies to mod sources and the port ledger. The agent is told to read the original.
- **The spec is not the only input.** The clean-room commits cite `cleanroom/shader-packs-spec.md`, but the spec is not in the repository. There is no evidence that the implementing session had *only* the spec, or that the spec was written by a different team.
- **The same agent family wrote the spec and the code.** The commits are co-authored by Claude Opus 5.5, the same agent family that works across the repository. If the spec was generated in the same session or from the same context, it is tainted.
- **No session boundary is documented.** There is no session ID, system prompt, model configuration, or transcript showing a fresh context. "No other loader's code read" is a sentence in a commit message, not a documented isolation.

A genuine AI clean room would look like this:

1. A **specification session** that reads the original and writes a behavior-level spec, reviewed to ensure it does not reproduce protected expression.
2. A **fresh implementation session** with only the spec: no repository access, no git history, no `.local`, no decompiled sources, no internet, no prior conversation.
3. The system prompt, session ID, model version and full transcript preserved.
4. The spec published, or produced under protective order, so counsel can compare it to the original.
5. A module-by-module comparison of the output to the original and the old code.

Horizon has produced none of these. It has produced a claim.

**Why "the AI wrote it from scratch" is not a defense.** An LLM's context is the clean-room boundary. If the original is in the context — as a file, a git object, a decompiled tree, or a prior turn — the model can reproduce it. "Write it from scratch" is a prompt, not a technical control. The legal test is still substantial similarity of protected expression; the tool used to produce it is irrelevant. A model trained on the original can also reproduce memorized fragments even without the file in context, which is why the transcript and the spec matter.

**Why the missing spec matters for legal analysis.** The spec is the one document that would let counsel test the claim: does it describe behavior at the abstraction level, or does it reproduce the original's structure, constants and order? Without it, the clean-room claim is unverifiable. The project should be required to produce it, under protective order if necessary. Its absence from the public tree is not proof of copying, but it means the defense cannot be evaluated — and the burden of proving a clean room is on the party asserting it.

Corroborating signs:

- **The timing is implausible for an independent rewrite.** 69 commits in three days, across a 6,000-line crate plus renderer integration, is consistent with AI-assisted translation from existing material, not a two-team clean room.
- **The project's own docs reversed the practice.** Before `7efdbdb39`, `docs/modpacks.md` said ports were written "with decompiled code as a local reference only"; after, it says "a mod's code is never decompiled, read, quoted or paraphrased." The same commit deleted the surveys that practice produced. That is a documentation change, not a change in method.
- **The comments were scrubbed after the fact.** `e80ee4d10` changes "as Iris has it" to a neutral property name. The behavior is unchanged; the attribution is removed.

A "clean room" is a factual claim about process. Horizon has not documented the process; it has asserted the conclusion.

**The results corroborate the process failure.** The deleted crate is not a subtle case: it contains Iris's test sentences, Iris's class names, Iris's `iris_*` identifiers, and function-level translations of Iris's `CommentDirectiveParser.findDirective` and `AbsolutePackPath.normalizeAbsolutePath`. That is what a non-clean-room translation looks like.

The new crate is structurally different in many places, which is a point in its favor. But the differences do not prove a clean room. They are equally consistent with a second AI pass over the same material, with the old code and the decompiled sources in reach, and with a spec that is not available for inspection. The one document that would distinguish the two — the spec — is missing. The project's assertion "no other loader's code read" is a conclusion, not evidence of isolation.

On the results alone, one cannot say the new code is a copy. But the clean-room *claim* is a claim about process, and the process evidence is absent. The burden of proving a clean room is on the party asserting it. Horizon has not met it.

The pattern across the repository is consistent: copy, get caught, delete, ask an AI to rewrite, call it clean room. The common factor is the absence of a clean intermediate spec and of any documented isolation. That is why the claim is not credible as a legal defense, even where the new code differs.

#### (c) The legal consequences

- **The rewrite is still a derivative if it is substantially similar to protected expression.** A clean-room failure does not cure the original license violation; it can create a new one. The original license (LGPL-3.0, GPLv2, or the Minecraft EULA) still governs the derived code, and the MIT grant is still unauthorized.
- **An undocumented clean-room defense is worse than no defense.** The party asserting a clean room bears the burden of proving it. A missing spec, missing session transcripts, and same-agent access invite the inference that the process was not followed. A label in a commit message is not evidence.
- **Willfulness.** The sequence — take, get caught, delete, rewrite, claim clean room — is evidence of knowledge. Under 17 U.S.C. § 504(c)(2), willful infringement can carry statutory damages up to **$150,000 per work**; § 505 allows attorney's fees. The removal commit and the docs reversal are exhibits.
- **False representations.** "Horizon contains no Minecraft code" and "the shader packs are being written again from a description of the pack format only" are statements the project has made to users and contributors. If they are false, they support unfair-competition and false-advertising theories (Lanham Act § 43(a)) and undermine the project's credibility on every other factual claim.
- **Spoliation.** Deleting the code, the spec, or the agent logs after notice can lead to adverse inferences or sanctions if litigation was reasonably anticipated. The removal happened after an Iris developer complained; the project moved its website to a private repository two days later. Counsel should demand preservation immediately.
- **Downstream liability.** The MIT grant remains ineffective as to the derived portions. Forks, distributors and users who relied on it are exposed; the project's own contributors may face claims.
- **DMCA § 1202.** Removing copyright management information (the Cull Leaves notice) can be a separate claim, though it is weak where the code itself was removed.

#### (d) Why the absence of a major court case does not make it legal

Copyright infringement is statutory. A court case is not a condition precedent to illegality; it is a condition precedent to a judgment. The elements are:

- ownership of a valid copyright (Minecraft, Iris, OpenJDK);
- access (the project decompiled the JARs; it cloned Iris; it ported the JDK);
- substantial similarity of protected expression (the admissions and the code comparisons);
- unauthorized distribution (MIT, not the original licenses).

The project's own admissions establish access and copying for Iris and OpenJDK. For Minecraft, the 6,490 citations and the algorithmic matches establish access and a strong case for translation. A court would apply existing doctrine — derivative work, substantial similarity, license conditions — not wait for a new precedent.

The absence of a reported Horizon case reflects enforcement choices and settlement dynamics, not legality. Most infringement disputes never reach a reported opinion. The question for counsel is whether the conduct falls within the exclusive rights and outside the licenses; on this record, it does.

#### (e) What a genuine clean room would require

If Horizon wants to cure the problem, it would need to:

1. Produce the specification, every revision, and the identity of who wrote it and what they read.
2. Show that the implementation session had no access to the original, the old code, the repository history, the `.local` tree, or the decompiled sources.
3. Preserve the session IDs, system prompts, model versions and full agent transcripts.
4. Share the spec with counsel (under protective order if necessary) so it can be compared to the original at the abstraction level.
5. Run a module-by-module comparison against the original and the old code.
6. Re-license the derived portions under the original licenses, or replace them with code that passes the comparison.

It has done none of these in public. The new shader crate may be a genuine rewrite — the structural comparison in §4.9 is consistent with one — but the project has not met the evidentiary burden its own defense requires. A spec kept private is not a clean-room defense counsel can test; it is an assertion that the other side must take on faith.

#### (f) Caveats

- A genuine rewrite can be lawful; the new shader crate is structurally different from the old one, so it may be.
- The missing spec is an evidentiary gap, not proof of copying.
- The legal outcome is uncertain; filtration and fair use could reduce the Minecraft claim, and the Iris/OpenJDK claims depend on the specific code and licenses.
- The YUNG/Lithostitched/CTOV replacements are not shown to be copied; they are a pattern to test, not a finding.

The point is not that every rewrite is infringing. It is that **"clean room" is a conclusion that must be earned with a documented process, not a label an AI can be prompted to produce.** Horizon's pattern — copy, get caught, delete, rewrite, claim clean room — is the opposite of that process.

## 7. What is *not* proven, and the counterarguments

A credible memo must state the weaknesses. The GPL claim in §4.7 and §6.0 and the Iris admission in §4.8 are not subject to most of them: they do not depend on substantial similarity, merger, or fair use, and the file headers or the commit message admit the provenance. The weaknesses below apply mainly to the Minecraft derivative-work theory.

1. **No literal Java was found in the repository.** The decompiled tree is gitignored. There is no file in the public tree that is a copy-paste of Minecraft Java, with the exception of the data tables (which are data, not code). This is true of Minecraft; it is not true of the shader crate, which is a Rust port of Iris and whose removal commit admits it. The verbatim test strings in §4.8(c) are copied expression, not just behavior.
2. **The Rust is idiomatic and re-architected.** It is not a mechanical line-for-line translation; types, ownership, error handling and module structure differ. A court could find it a new work that merely shares behavior.
3. **Behavior and function are not copyrightable.** Many of the matches are "same result", which is lawful. The case depends on the *expression* residues identified in §4.
4. **Constants may be facts or ideas.** Individual numbers like `0.04` are not protectable. The strength is the *selection and arrangement* across hundreds of methods, not any single number.
5. **Decompilation for interoperability has fair-use precedent.** *Sega* and *Connectix* are real. Horizon will argue it needed to read the code to make a compatible game.
6. **The project has a public clean-room story** ("checked against vanilla with differential harnesses", "vanilla first"). It will argue the harnesses, not the source, are the specification. The counter is the repository's own admissions that authors read and translate the source.
7. **The most damaging evidence is off-repo.** The `.local` decompiled tree, AI agent transcripts, Discord discussions and the maintainer's local build artifacts are not in the public repository. They are where direct proof of copy-paste would live.
8. **No proof of access to a specific copyrighted work beyond the public JAR.** This is easily met: the JAR is public, the project pins it, and the decompilation is documented.
9. **Some of the matches could be convergent.** For example, any implementation that wants bit-identical noise must use the same constants; the argument is that Horizon *chose* bit-identical output, and its own docs say so. Convergence is less plausible for the gradient-table duplicates, the shuffle direction, the `1e-7f` widening and the heap tie-breaking.
10. **The legal outcome is uncertain.** *Google v. Oracle* shows that even large copying of functional elements can be fair use. The case must be built on the non-functional residues and the market harm.
11. **The OptiFine allegation does not hold up in the sampled modules.** OptiFine 26.2's random-entity seed, CTM hash, chunk-visibility strategy, smoothing and region rendering are all implemented differently in Horizon; the CEM function set matches because the format requires it. The claim may be true for modules not sampled, but it should not be asserted without the specific method and version. (See §5.5.)
12. **Deleting a file does not delete the distribution.** The shader crate is gone from `HEAD` but is still in `main`'s object graph and in 285 tags; a normal clone transfers it. A history rewrite would be needed to stop future distribution, and even that would not undo the 16–24 October distribution or reach existing clones and forks. The removal commit reduces the ongoing exposure only for users who fetch a rewritten history, which has not happened.

- reproduces, in at least six independent subsystems, arbitrary implementation choices that have no public specification and no plausible independent origin;
- shipped a 6,638-line Iris-derived shader crate under MIT, then removed it from `HEAD` while leaving it in `main` and 285 tags; and
- rewrote its own contributor documentation from "decompiled code as a local reference" to "never decompiled, read, quoted or paraphrased," in the same commit that deleted the surveys of other mods.

The single strongest fact is not the Minecraft analysis at all. It is commit `4e7c25bb5`, which says in terms:

> "A developer of Iris showed that Horizon's shader pack code was written from Iris's source. This removes it..."

That is a party admission of copying an LGPL-3.0 project into an MIT workspace. The project repeats it on its public "How Horizon is built" page, the page users are pointed to for "why it's safe to run." It is backed by verbatim copies of Iris's `CommentDirectiveParser` test strings and by Iris's internal `iris_*` identifiers. And the code is still in the repository: `b22583d05` is an ancestor of `HEAD`, the blob is in `main`'s object graph, and 285 tags contain it, so every normal clone still receives it. Deleting the file at the tip did not delete the distribution.

The strongest single sentence for a legal memo on the Minecraft side is from the project's own agent instructions:

> **"Translate the vanilla method, don't reinvent it: same order of operations, same constants, the same random draws in the same order."**

That is a description of derivative-work production, written by the project, for the project, and applied at the scale of a million lines.

The "clean room" claim does not survive the record. The same agent family wrote the old crate and the rewrite; the old code and the decompiled sources are in the same repository; the spec is not published; the session transcripts are absent. A clean room is defined by information isolation, not by a commit message. On the evidence available, the rewrite is a second pass over the same material, not an independent implementation.

The MIT license is therefore not a clean title. It is a grant the project had no authority to make as to the Minecraft-derived portions, and it exposes every downstream user, fork and distributor. That is the radioactive problem, and it is documented in the repository itself.

There is also a second, simpler defect. The repository ports OpenJDK's `java.lang.FdLibm` and HotSpot's AArch64 trig stubs into `horizon-core` and distributes them under MIT. The file headers say "verbatim"; the OpenJDK sources are GPLv2 (the HotSpot file without the Classpath Exception), and GPLv2 §0 covers a work "translated into another language." That claim does not need a substantial-similarity expert, a fair-use analysis, or a comparison of 6,490 citations. It needs the two files and the license text. It should be the first thing counsel reads.
